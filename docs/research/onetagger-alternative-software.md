# Alternative software that fills OneTagger gaps

Research checked 2026-10-20 against official product documentation, maintainer repositories and release records. This is documentation/source evidence, not execution or native-app compatibility validation. No software was installed, no closed app was automated, and no music, account or license data was accessed. Prices are deliberately omitted; license/business-model distinctions matter more to this plan.

## Decision

Borrow **beets' unattended-import and exception model**, **Picard's release-aware review**, **Mp3tag's explicit batch-edit/actions/artwork controls**, **Lexicon's DJ taxonomy and path-aware library model**, and **Kid3's precise frame identities and real automation contracts**. Implement those ideas through CueRithm's existing Rust services, persistent Incoming queue and design system. TagScanner supplies another useful preview-first organization reference. Mixed In Key primarily overlaps the validated native analysis already present; it does not solve the missing catalog-match/rename service.

Do not make successful Incoming preparation depend on any separately installed GUI product. Do not infer a tagging API merely from command-line launch arguments or an open-source license.

## Automation: exact boundaries

- **beets is genuinely automation-capable**: CLI supports import/modify/move/write, quiet/resume/incremental policies. Export plugin supplies JSON/JSONL/CSV/XML and can distinguish file tags from database data. The Web plugin adds limited browse/play and REST access, default read-only; it is not the same as a complete remote import pipeline. [CLI](https://docs.beets.io/en/stable/reference/cli.html), [export](https://docs.beets.io/en/stable/plugins/export.html), [Web](https://docs.beets.io/en/stable/plugins/web.html)
- **Picard has command-assisted GUI processing**, including LOAD/LOOKUP/SCAN/SAVE_MATCHED/QUIT and file-based command queues. However new3.0 `picard-cli` is **not** a headless tagger: pinned3.0.2 source registers plugins, profiles and completions only. Do not describe it as a tagging HTTP API or daemon. [Executable commands](https://picard-docs.musicbrainz.org/en/latest/usage/exec_commands.html), [pinned CLI source](https://raw.githubusercontent.com/metabrainz/picard/release-3.0.2/picard/cli/__init__.py)
- **Mp3tag Windows launch arguments are limited** to opening/adding files/directories. Official docs explicitly state interactive design and no further commands planned. Action groups are user-run internal workflows, not a headless API. No official supported Mac headless tagging contract was established in this review. [Windows CLI](https://docs.mp3tag.de/command-line/), [Mac product](https://mp3tag.app/)
- **TagScanner scripts are transformations/export templates inside its GUI**; no maintained general CLI/API contract established from official pages reviewed. Old PDF describes Preview then Run/Rename/Save, not daemon automation. This is a documentation limit, not proof no undocumented switch exists. [Download/scripts](https://www.xdlab.ru/en/download.htm), [manual](https://xdlab.ru/files/ts_manual.pdf)
- **Lexicon has a real Local REST API**, opt-in and requiring Lexicon running, with documented tracks/search/playlists/custom tags/playback. Documentation notes no authentication, all-interface listening and serialized mutations. This is a possible explicit interoperability adapter, not a redistributable tagging engine; do not enable or call the user's app during research. [Local API](https://www.lexicondj.com/docs/developers/api)
- **Kid3 has a real CLI plus JSON command format**, and optional QML/D-Bus surfaces, unlike most GUI-only editors. Its immediate rename operations and per-format rating behavior still need careful orchestration; CLI presence does not guarantee transactional safety. [CLI](https://docs.kde.org/trunk_kf6/en/kid3/kid3/kid3-cli.html), [project](https://kid3.kde.org/)
- **Mixed In Key**: official material reviewed establishes application-driven analysis and tag/cue integration, not public batch CLI/API/SDK. External file tags can be read as provenance; its measured values must not become inputs or reference labels for CueRithm predictions. [Integration](https://mixedinkey.com/workflows/dj-software-integration-guides/)

## Important limits and acceptance lessons

1. **Do not inherit another application's confidence label as truth.** Release choice, recording identity and version are separate. Picard/beets add better review mechanisms; neither documentation proves match correctness for a DJ corpus. Claims such as MIK's higher accuracy are vendor claims, not comparative evidence collected here.
2. **A polished editor can still have preservation bugs.** Mp3tag Mac2026 changes mention unknown MP4-atom retention, unsaved edits and slash-path problems; TagScanner2026 mentions file-damage protection and case-only renames. Beets2.14.1 fixes destination escape from empty leading path fields. These are concrete regression-case ideas, not evidence the apps are unsafe today. [Mp3tag changes](https://mp3tag.app/changelog_short/changelog.html), [TagScanner history](https://www.xdlab.ru/en/history.htm), [beets release](https://github.com/beetbox/beets/releases/tag/v2.14.1)
3. **Current Lexicon enrichment differs from historical source selection.** Its current manual says Find Tags & Album Art uses SonoVault only and has an Original release option that removes remix text. Learn the field/provenance UI, but do not assume selectable Beatport/Spotify provider parity or import remix stripping as safe default. [Current enrichment manual](https://www.lexicondj.com/manual/find-tags-and-album-art)
4. **No generic editor promises all external DJ databases follow a rename.** CueRithm must own its move transaction and target-sync consequences. Native frame/PCM preservation, undoability and database identity each require separate checks.
5. **Open code and online data have separate terms.** MIT/GPL permission does not confer unrestricted reuse of MusicBrainz supplementary data, Discogs/Last.fm services, cover images or provider credentials. Provider access terms belong in the existing separate provider assessment; do not bundle keys or scrape a closed service because a GUI can query it.

## Proposed plan adjustments

- Keep automatic Incoming as default: decode/full native DSP → ordered enrichment → configured metadata actions/canonical cleanup → cue refresh → staged tag verification → optional organized path plan → durable publication/identity update → ready. Failures/ambiguity remain visible and retryable with usable analysis retained. This sequence is a CueRithm proposal, not behavior asserted for these alternatives.
- Add a **Review** state/filter and shared inspector with candidate/source/release evidence, field/artwork diff and Keep/Set/Clear. Persist drafts/save queue across search, tab changes and close; retain the bottom waveform/player.
- Add an **Organization** Settings page while retaining existing Settings navigation/save behavior. Provide in-place rename, move-to-library and copy-to-destination as distinct modes; preset tokens, optional groups, original filename, version, stable collision handling and full-batch previews. Avoid exposing three incompatible script languages.
- Use existing categorized tags for a fast human-tag inspector; do not create a second OneTagger-style taxonomy. Add keyboard hints, wrapped/searchable chips and optional native/DJ field mapping.
- Treat beets/Picard/Kid3 as sources of selected concepts and independent synthetic-fixture validation; closed tools as product/compatibility references. A future opt-in Lexicon API connector is separate from the core Incoming pipeline.
- Preserve CueRithm's shipped decoder resources, native DSP, measured key/BPM and single whole-track energy. General raw-frame editing and external provider engines should not replace or silently bypass those invariants.
