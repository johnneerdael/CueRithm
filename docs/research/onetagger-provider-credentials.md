# OneTagger provider credentials and accountless capabilities

Checked 2026-10-21 against public service documentation and OneTagger commit `36523f71f2d9a5947912f3cb930f1a31fcb2e3ee`. No personal credential files were accessed, accounts created or tokens obtained. After the documentation review, one explicitly authorized anonymous Discogs search request was made with a public sample query; its sanitized result is recorded below. No other provider API was called. Documentation/source inspection and this single request do not establish broad endpoint health or successful tagging.

The pinned builders mark **Spotify, Discogs and BPM Supreme** as requiring authentication. That is an upstream implementation decision, not a complete service capability model: current anonymous Discogs search also returned HTTP200 in the bounded check below, while Musixmatch's supported API requires a key even though OneTagger's unofficial desktop-client adapter requests no user credentials.

## Discogs: current anonymous search observation and optional authentication

Keep CueRithm usable without a Discogs account. Offer the capabilities available in that mode rather than treating the entire provider as either authenticated or unusable.

- **Public ID-based enrichment:** release/master/artist/label resource lookup is the accountless foundation. Known embedded Discogs IDs or an explicitly selected public resource can supply useful data without free-text database search. The official Discogs-owned SDK demonstrates fetching a release with only an identifying User-Agent. That SDK is archived, so it is supporting historical primary evidence, not a current runtime test.
- **Database search:** one anonymous `GET /database/search?q=Daft%20Punk&type=release&per_page=1&page=1` returned HTTP200 with JSON and no authentication error on 2026-10-21. The request used an identifying CueRithm development User-Agent and no authorization, cookies, curl configuration, redirects, retries or solver. Support anonymous search rather than imposing the historical token gate. This verifies that request's access outcome; it does not validate metadata accuracy, every filter, sustained bulk access or future availability. The web documentation's 403 response was a documentation-fetch limitation, not proof that the API requires authentication.
- **Personal token versus application credentials:** the official authentication guide distinguishes a generated personal user token from OAuth consumer key/secret plus user authorization. Do not bundle a developer's personal token as every installation's identity. Application-only credential modes need not be introduced merely to unlock the observed anonymous search route. No credential value was inspected or authenticated mode tested.
- **User-selected rate caps:** enforce at most **25 requests/minute without authentication** and **60 requests/minute with valid authentication**. These are product requirements even if service ceilings change. Credential presence alone must not switch to 60. Share the budget across workers/pages/lookups and honor stricter server headers/backoff; do not turn authentication/rate failures into no-match.
- **Upstream adaptation needed:** the low-level OneTagger client starts at 25 and changes to 60 when a token is set, but its builder always sets and validates the configured token. It also exposes a rate override. Optional authentication and hard upper caps therefore require deliberate changes, not copying that builder unchanged. [Pinned client and builder](https://github.com/Marekkon5/onetagger/blob/36523f71f2d9a5947912f3cb930f1a31fcb2e3ee/crates/onetagger-platforms/src/discogs.rs#L27).

Sanitized access evidence from that single request (no search-result dataset retained or published):

| Observation | Value |
|---|---|
| Authentication supplied | None |
| HTTP status | 200 |
| Content-Type | application/json |
| X-Discogs-Ratelimit | 25 |
| X-Discogs-Ratelimit-Remaining | 25 |
| X-Discogs-Ratelimit-Used | 0 |
| API authentication/error message | None returned |

These are the received header values; the remaining/used figures do not establish a larger burst allowance or waive shared pacing.

## Consequence for the selected provider program

End users do not need to register developer applications merely to use CueRithm. Keep public lookup providers accountless where supported; request personal authentication only for an independently chosen provider/capability. If Spotify is ever accepted, design an application-owned registration with a suitable installed-app flow rather than requiring every user to create client credentials. Existing Spotify feature exclusions remain unchanged.

SonoVault is separate from the twelve pinned adapters: users choosing it provide a personal API key, with the approved [free-key signup link](https://sonovault.now/signup). Musicfetch remains excluded. This inventory does not approve additional adapters or extend PR3 scope.
